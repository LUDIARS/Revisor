# review-concurrency — 審査の受け付けと絞りの位置

## 1. 審査は複数本が同時に進む

**審査の同時実行数は 1 にしない。**

遅いモデルレビュー 1 件が枠を占有すると、後続の PR が**空いている**登録テスト /
Anatomia / セキュリティのワーカーへ届かなくなる。 専用ワーカーを関心ごとに分けた意味が
そこで消える。 待ち行列が伸びても同時実行が 1 のままなら、 ワーカー数を増やしても
待ち時間は縮まない。

受け付け段 (`persistent-queue.mjs` と `job-store.mjs`) 自体は次だけを担い、 同時実行数の
判断は持たない。

- lifecycle の記録 (queued / running / 終局)
- 同一 (repository, number, head) の重複排除
- 中断された job の拾い直し

## 2. 同時実行数は drain が決め、実行容量は段階プールが持つ

同時に審査へ入れる PR の本数は、 短命ワーカーの drain
(`review-job-scheduler.mjs` の `drainReviewJobs`) が `workerCount` を上限として決める。
そのうち `fastLaneSlots` 本は fast lane のために空けておき、 standard がキューを
埋め尽くしても急ぎの審査が入れるようにする。

実際に走る高価な処理 (登録テスト・Anatomia 解析・モデルレビュー・セキュリティ診断) は
段階ワーカープール (`review-stage-workers.mjs`) の中で走る。 プールは**関心ごとに独立**
していて、 遅いモデルレビューがテスト用のワーカーを食い潰さない。外側 scheduler の上限は
PR 全体の数、各プールの上限はその関心ごとの実行数であり、役割は異なる。

**`workerCount` は 2 か所に効く** — drain の同時審査数と、 段階プール 1 つあたりの本数。
片方だけを見て「設定を上げたのに速くならない」と判断しない。 実際の稼働本数は
`/api/review-work` で確認する。

## 3. 取り込みだけが直列

**全ゲートを通過した PR をステージして base へ載せる段は、 1 本ずつ行う。**

base を進める操作は互いに順序依存であり、 同時に走らせると片方が必ず「base が動いた」で
落ちる。 直列化の位置はここであって、 審査の受け付けではない。

- squash / publish は `publication-coordinator.mjs` のロックで直列化する
- 走行中のマージは service 内で追跡し、 同じ PR に二重のマージを走らせない
- 載せ替え (`review-diff-scope.md` 規則 3) は取り込みの一部であり、 同じ直列区間に入る

## 4. 実行経路を増やす変更は同時実行モデルを変えない

**「審査を CLI からも発行できるようにする」は経路の追加であって、 同時実行モデルの変更では
ない。** 経路を増やす変更が、 サーバが持っていた並行性を落としてはならない。

daemonless 化の目的は「サーバの生存に審査の進行を依存させない」ことだった。 それは
**誰が審査を起動するか**の話で、 **何件を同時に走らせるか**とは独立している。 短命ワーカーを
足すこと自体は正しく、 その中の drain を逐次にしたことが目的を超えている。

新しい実行経路を足すときは、 既存経路が満たしていた invariant (本書 1〜3) を、 新経路でも
同じように満たすこと。 経路ごとに並行性が違ってよい理由は無い。

## 5. なぜ明文化するか (2026-08-11)

この invariant は一度失われた。 経緯を記録する。

- `19ab52c` (初版) の `architecture.md` は「キューの同時実行数とワーカープロセス数は同じ
  設定を使い、 プールが実行できる以上の run を受け付けない」と書いた。 当時は正しかった。
- `36660a3` (2026-08-08) が段階ワーカーを関心ごとに分割し、 受け付け側を
  `concurrency: Number.MAX_SAFE_INTEGER` にした。 絞りがプールへ移った。
  **`architecture.md` は更新されなかった。**
- `bc5e235` (2026-08-10) の daemonless 化が、 コード側のコメントではなく古い
  `architecture.md` の記述に従い、 受け付けを短命ワーカー 1 本の逐次ループに置き換えた。
  段階プールは残ったが、 その手前で 1 件ずつに絞られるようになった。
  **この変更の目的は審査を CLI から発行できるようにすることであって、 同時実行モデルの
  変更ではなかった** (規則 4)。 経路の追加がサーバ側の並行性を落とした。

結果、 `workerCount` を上げても審査は 1 件ずつのままになり、 待ち行列が 18 件まで伸びた
状態でも同時実行は 1 だった (2026-08-11 実測)。 `run-worker` を入れ替えて段階ワーカーを
4 種 × 3 = 12 本立てても、 その手前で 1 件ずつに絞られていた。

同日、 fast lane の実装 (`review-job-scheduler.mjs` の `drainReviewJobs`) が並行 drain を
入れたことで解消した。 規則 2 はその実装を正本として書いている。

**教訓**: 絞りの位置を動かす変更は、 コードのコメントだけでなく `architecture.md` を
同時に直す。 仕様が古いまま残ると、 次のリファクタが仕様に従って挙動を戻してしまう。
本書はその再発防止として、 「同時実行数をどこが決めるか」 を仕様側の正本にする。

## 検証

- 遅いモデルレビューの実行中に、 別 PR の審査が開始できること (同時実行が 1 にならない)
- standard がキューを埋めている状態でも、 fast lane の予約枠ぶんは入れること
- 取り込み (squash / base 前進 / publish) が同時に 2 本走らないこと
- 走行中の審査を残したまま「キューが空になった」と判断しないこと
